# document scan, repo tickets, tool venvs and constrained approvals

## Summary

The branch added a whole subsystem — scanning, repo tickets, the two tool-venv kinds, the probe
token and constraints-bound approvals — and none of it was in the manual. AGENTS.md asks CLI
changes to be reflected in the usage guide, and a feature nobody can find is not shipped.

## Changes

**`docs/USAGE.md`** (201 → 317 lines):

- *Find what is on a machine*: the two lanes and the unclassified row, what the walk skips and
  stops at, `--depth`/`--exclude`, and why `--list` is the safe first step (no git, no `gh`, no
  tools, no database) — with the honest note that a real scan runs git in each checkout, where a
  configured clean filter is the owner's own program.
- *Repo tickets*: what `.netwatch` contains, the four finding types and staleness as a lead, the
  ownership rule and `report` as the explicit override, and the publication mechanics (refusals,
  temp-then-rename, leftover cleanup).
- *Register environments from a scan*: index-into-the-stored-run, the five-item all-or-nothing
  batch, what registration re-verifies, and the suffix rule for a taken name.
- *uv tool and pipx environments*: how to register one, what `check` reads, the probe token and
  why deleting it is safe, the exact install command, the two ways approval is constrained
  (retained bounds in the artifact, markers evaluated in the venv), the recorded index replay
  with redacted-at-rest credentials, the ordered apply verifications, the five conditions behind
  `applied`, and a table of lifecycle states with the action that clears each.
- *Retiring a target*, plus `scan`/`report` rows in the cache-and-network table, the tool-venv
  apply row and gating note in *Updates*, and schema 11 with the constraints directory in
  *Storage*.

**`docs/DESIGN.md`**: seven new modules in the table (`scan`, `tickets`, `userlane`, `pins`,
`probe`, `lifecycle`, `venvflow`) and a new section stating the behavior to preserve — lanes and
the stop-at-repo-root rule, `--list` touching nothing, repos never becoming targets, registration
from a stored run, the manager naming the tool, approval bound to an installation, origins gating
planning, what `applied` means, lifecycle as one machine with column-held flags and guarded
writes, and uv running from the state directory.

**`README.md`**: the feature list, a *Find what is on a machine* section with the scan/`report`
commands, a *Check a tool venv* section, and reference links that name the new guides.
