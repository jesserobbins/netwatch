# rework 7: launchers come from manager exposure, recovery is named, clears are guarded

## Summary

The seventh audit found launcher verification was not the specified one: the expected list came
from the distribution's `entry_points.txt`, so a tool that is a native binary — ruff, uv — had no
expected launchers at all and a deleted launcher still read clean.

## Changes

- **Launchers come from what the manager recorded as exposed**: uv's receipt entry points and
  pipx's metadata app paths, each with the path it was installed to. A missing exposed launcher
  is `broken`; a native binary whose text cannot be read is reported as
  `launcher not entry-point-verifiable` with its bin directory named, so the report says what was
  and was not checked instead of implying everything was.
- **The bin directory is the recorded one**, not one re-derived at check time: a later
  environment change does not re-point what this target is expected to expose.
- **pipx's exposed directory is its own** (`PIPX_BIN_DIR`, default `~/.local/bin`), not the venv's
  bin.
- **`add --kind uvtool|pipx` works through the CLI** (`choices=KINDS + VENV_KINDS`); the earlier
  fix only covered `adapters.target`, which is why the plan's item looked done and was not.
- **`not_bindable` is visible**: the report names the recovery — delete `<venv>/.netwatch-probe`
  and re-run check, which is safe because netwatch writes a fresh one.
- **Preview's `not_bindable → live` write is generation- and state_seq-guarded**, so it cannot
  land on a retired row.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 398 tests, OK.
- `test_check_reports_a_broken_launcher` now supplies the manager's receipt entry point, which is
  where the expectation comes from, and asserts the broken launcher is a finding.
- Live check after the change: deleting an exposed launcher from the recorded bin directory makes
  `check` report it, where before the report was clean.
