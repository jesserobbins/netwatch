# rework 2: constraints bound the install, markers evaluate, origins gate, raw index used

## Summary

Second audit round: the install was selected under retained bounds but not constrained by
them, markers were never evaluated, origin policy was recorded and not enforced, raw index
credentials never reached uv, three lifecycle paths were unreachable, the approval was not
bound to uv's configuration environment, and cleanup/expiry skipped the scan paths.

## Changes

- **Constraints bound the install**: `pins.derive` returns the bounds that were in force, and
  `_write_constraints` writes them into the artifact next to the pins, so `-c` constrains
  transitive resolution rather than merely describing it.
- **PEP 508 markers are evaluated** against the venv's own interpreter (`pins.marker_environment`
  reads os_name, sys_platform, python_version, implementation and platform fields with
  `-I -S`; `_marker_true` calls `Marker.evaluate`). A venv without a runnable interpreter
  refuses with a clear error instead of guessing.
- **Origin policy is enforced** in `preview`: an undetermined origin makes the target
  unplannable, and direct/VCS/local installs are held at their current version with a lead.
- **Raw index options reach uv**: `describe` returns `index_options` (raw) and
  `index_options_redacted`; scan records and plan bodies store only the redacted form, and
  apply rebuilds the argv from the live raw values at claim time, refusing if the redacted
  shape no longer matches.
- **Lifecycle paths**: an unreadable identity read is now a *complete* observation, so two of
  them set `identity_mismatch`; a recovering check publishes a token like any other; and
  revival resets `state` to `live`.
- **Approval bound to uv's configuration environment**: `fingerprint(state_dir)` hashes the
  uv configuration files discovery would read, and the local runner pins cwd to the state
  directory so a repo-local `[tool.uv]` cannot shape resolution.
- **Cleanup and expiry reach every command**: `scan`, `scan --register` and `report` run both;
  constraints live beside the database that recorded them, so a custom `--db` no longer
  leaks files into the default state directory.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 373 tests, OK (10 new in
  `tests/test_audit_fixes.py`, plus updates to `test_pins`/`test_venvflow`).
- New tests cover exactly the paths the audit named: a retained bound appearing in the
  constraints artifact, a marker-guarded bound blocking a candidate and a false marker
  letting it through, an undetermined origin refusing a plan, a VCS install held at its
  version, the raw credential in the rebuilt argv with none in the stored plan, two
  unreadable identity reads setting `identity_mismatch`, recovery publishing a token,
  revival from `unresolved_path` returning to `live`, and cleanup agreeing with preview
  under a custom database.
