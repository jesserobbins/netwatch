# lifecycle flags are read from their columns, not the body

## Summary

Verifying the launcher and recovery fixes surfaced a bug of my own: `removed`, `state`,
`generation` and `state_seq` live in the *columns*, but several checks read them from the target
body, where they do not exist. A retired target therefore still counted as a live co-claimant on
the same venv, and recovery from an out-of-service state never happened.

## Changes

- `Store.target_rows()` returns each target's body with its lifecycle columns merged in, and is
  the read used wherever those flags matter.
- `venvflow.co_claimants` skips retired rows properly, so a removed twin no longer blocks
  recovery and the "out of service" refusal only fires for a real conflict.
- `workflow.apply`'s same-venv conflict check uses the columns *and* is scoped to the venv-bound
  kinds, so conda/uv/npm project targets that legitimately share a directory are not refused.
- `scan.register`'s blocking set reads `state`/`removed` from the columns too.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 398 tests, OK.
- Live: after retiring the twin on the same venv, a check with a malformed probe reaches the
  report path again instead of refusing with "out of service".
