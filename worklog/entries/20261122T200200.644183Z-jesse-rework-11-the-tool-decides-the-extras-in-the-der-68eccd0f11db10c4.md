# rework 11: the tool decides the extras, in the derivation and in pipx

## Summary

The audit found the label-for-tool substitution alive in two more places, and one of them
silently dropped the extras Task 7 requires on the tool's own pin.

## Changes

- **`pins.derive` is given the manager's tool**, through one `tool_of(t)` helper, so the
  "observed extras on the tool's own pin" rule fires for labelled targets. Live: the same black
  venv registered as `blabel` now plans `black[colorama]==26.10.1` with `black[colorama]==26.10.1`
  in the constraints artifact (before: `black==26.10.1`, with the body still recording the extras,
  so the plan contradicted itself and the gate passed).
- **pipx extras parse the recorded spec properly**: `black[colorama]==24.8.0` ends at a version,
  not at the extras, so the bracket-only parse saw nothing. `packaging.requirements.Requirement`
  reads it, with the bracket split kept as a fallback.
- **Findings name the tool**, so a labelled target's launcher and consistency findings carry the
  installed version instead of `null`.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 418 tests, OK.
- Live, real uv: a uv-tool black venv installed with `[colorama]`; `scan` records
  `extras=['colorama']`; registered as `blabel`, `preview` returns pins
  `[{'name': 'black', 'version': '26.10.1', 'extras': ['colorama']}]` and the artifact reads
  `black[colorama]==26.10.1`.
- Tests: ToolVersusLabelTests (a labelled target's pin carries the tool's extras) and
  PipxExtrasParseTests (a version-pinned pipx spec still yields its extras) — the latter is the
  case the suite had no fixture for at all.
