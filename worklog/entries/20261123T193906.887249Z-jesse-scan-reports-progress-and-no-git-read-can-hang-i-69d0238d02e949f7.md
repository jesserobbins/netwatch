# scan reports progress and no git read can hang it

## Summary

`netwatch scan ~/GitHub` printed nothing for minutes, which is indistinguishable from a hang, and
in one respect it really could hang: `tickets.git` ran `subprocess.run` with no timeout, so a git
read that waited — a stalled mount, an index lock, a credential prompt — blocked the whole scan
forever with no output and no way to tell which checkout it was on.

## Changes

- **Progress on stderr**: `scan.run` takes a `progress` callback; the CLI sends it to stderr. One
  line per classified item (`[3/25] repo  some-checkout`), one when a checkout's reads start, one
  when its ticket is written. Stdout keeps only the summary, skipped and incomplete lines, so
  `--json` stays clean and `--quiet` gives a scriptable run.
- **No read can hang**: git runs with a 60-second timeout, `stdin=DEVNULL`, `GIT_TERMINAL_PROMPT=0`
  and an empty `GIT_ASKPASS`, and a timeout or spawn failure becomes an `Error` naming the repo and
  the bound.
- **One bad checkout does not stop the scan**: `tickets.collect` records a failed git read as an
  incomplete reason instead of raising, and the CLI prints `incomplete: <path> (<reason>)` in the
  summary, so a repo nobody could read is visible rather than silently absent.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 432 tests, OK.
- `tests/test_scan_run.py`: one progress line per item plus the leading summary; no callback means
  no output; a timed-out git read is recorded as incomplete rather than raised; the real runner is
  called with `timeout=GIT_TIMEOUT`; and a repo whose reads fail is named in `result["incomplete"]`.
- Run by hand: `scan /tmp/lt/tools` printed `scanning …: 4 items`, `[1/4] user black …`, then the
  summary; `--quiet` printed the summary only; `scan /tmp/prog-demo` showed `reading mine` and
  `ticket written: 1 finding`; a synthetic stalled runner produced
  `git did not answer within 60s in /tmp`.
