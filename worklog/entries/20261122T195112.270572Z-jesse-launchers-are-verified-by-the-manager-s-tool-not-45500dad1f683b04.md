# launchers are verified by the manager's tool, not the operator's label

## Summary

The audit found the last instance of the label-vs-tool mistake: `_launchers` looked the
distribution up by the operator's label, so on a labelled pipx target every healthy console script
was reported as "declares no entry point in the distribution's metadata" — a false diagnostic on
the check and status surfaces, on the very route the previous round's labelled-`add` fix exists
for. The identity code had already been corrected for this; the launcher path was missed.

## Changes

- `_launchers` asks `pins.launchers` for the **manager's tool** (`t.get("tool") or t["name"]`), so
  the entry-point verification runs against the registered distribution whatever label the
  operator chose.
- `LabelledLauncherTests` exercises exactly that: a labelled target whose tool ships a console
  script, asserting the launcher is `ok` rather than a lead. The earlier labelled-add test used a
  package with no console scripts, which is why nothing caught this.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 416 tests, OK.
- Live on isolated pipx venvs registered through the supported route:
  `add mylabel2 pipx --path .../venvs/black` → `_launchers` = `[('black','ok'), ('blackd','ok')]`
  (previously two leads), and `add mylabel pipx --path .../venvs/ruff` → `[('ruff','not-verifiable')]`,
  which is the correct verdict for a native binary.
