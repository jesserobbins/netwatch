# repo lane: findings, leads and inert .netwatch tickets

## Summary

A checkout is not an environment netwatch should manage, but a repo whose lockfile drifted, is
uncommitted, or pins a vulnerable version is exactly what a scan should surface. It gets a
file instead of a registration.

## Changes

- `netwatch/tickets.py`: `collect` (unpinned / not_revertible / drifted / advisory findings,
  staleness as a lead, incomplete collection recorded rather than swallowed), `render`
  (human-legible head, fenced JSON tail, header first line), `write` (lstat refusal for
  anything not a regular file, header check for foreign tickets, temp file with a 32-hex
  name, **pre-rename re-verification**, `os.replace`), `should_write` (a scan that
  collected nothing never overwrites and never invents a ticket).
- All git invocations go through `git()`, which carries `--no-optional-locks`, the
  `core.fsmonitor`/`core.untrackedCache` overrides and `log.showSignature=false` /
  `--no-show-signature`. Running it against real git caught two ordering mistakes: the
  top-level options must precede the subcommand, and `--no-show-signature` must follow it.
- OSV queries reuse `sources.fetch`/`sources.osv`, so there is one client.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 194 tests, OK (18 new).
- Live, real git, real files:
  - scratch repo with `pyproject.toml` and no `uv.lock` → ticket written, header first
    line, `unpinned` finding with the exact action, fenced JSON carrying the same payload.
  - `.netwatch` symlinked to a sibling file → `Refused: .netwatch is not a regular file;
    nothing was followed or written`, target file unchanged.
