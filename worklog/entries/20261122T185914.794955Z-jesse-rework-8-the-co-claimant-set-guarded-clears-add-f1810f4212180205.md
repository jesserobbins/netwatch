# rework 8: the Co-claimant set, guarded clears, add records the venv facts, preview p0/p1

## Summary

The eighth audit found the claim sets contradicted the spec: every non-removed row counted as a
co-claimant, including `unresolved_path`, and any co-claimant silenced an *in-service* target —
which the spec says publishes normally while only the demoted twin stays quiet.

## Changes

- **Co-claimant = `removed=0` and `state != 'unresolved_path'`**, exactly as the Store section
  defines it: a row whose recorded path is gone cannot be holding the venv.
- **An in-service target publishes beside a twin.** `publishable` now silences only an
  out-of-service target (unless this run recovered it), and recovery is blocked while a
  co-claimant exists.
- **The `not_bindable → live` writes are generation- and `state_seq`-guarded** in both places
  (the save path and the (p11) no-eligible-update branch).
- **`add --kind uvtool|pipx` records `realpath`, `bin_dir`, extras and redacted index options**,
  and refuses a venv another target already tracks — otherwise the identity rule silently did not
  apply to hand-registered targets.
- **Preview does the (p0) token read and the (p1) stale-temp cleanup** before publishing, so a
  malformed or unreadable probe is decided before the resolution bracket rather than after it.

## Validation

- `.venv/bin/python -m unittest discover -s tests -q` — 406 tests, OK.
- New tests: an `unresolved_path` sibling, an `identity_mismatch` twin and a removed row each
  leave a healthy target publishing; preview cleans a stale probe temp; preview refuses an
  unreadable probe before resolving; `add` records `realpath`/`bin_dir` and refuses a shared venv.
- Two older tests were corrected: they encoded the contradiction (a live target silenced by a
  twin), which is why the suite had been passing with the wrong rule.
